一次线上延迟告警让我们重新审视整条 RAG 链路。真正拖慢响应的并不是大模型本身，而是散落在召回、重排与上下文拼装之间的等待。

> 性能优化不是把每一步都做到最快，而是让关键路径上不再出现没有价值的等待。

## 先画出真实的关键路径

最初的监控只记录了接口总耗时。它能告诉我们系统变慢了，却无法回答时间究竟消耗在哪里。第一步不是改代码，而是为请求补齐阶段级追踪：

1. 查询改写与向量化；
2. 多路召回；
3. 候选合并与重排；
4. 上下文裁剪；
5. 首个 Token 返回。

拆分之后，P95 延迟的构成变得清晰：召回阶段存在串行请求，重排阶段传输了远超需要的文本，而生成阶段只占总时间的一小部分。

| 阶段 | 改造前 P95 | 改造后 P95 | 主要动作 |
| --- | ---: | ---: | --- |
| 查询处理 | 24 ms | 18 ms | 缓存稳定查询 |
| 多路召回 | 112 ms | 46 ms | 并行化与提前终止 |
| 重排 | 96 ms | 51 ms | 缩小候选与批处理 |
| 上下文组装 | 43 ms | 21 ms | 去重与预算裁剪 |

## 召回：并行不等于无节制并发

原链路依次访问关键词索引、向量索引和历史问答库。三个结果互不依赖，因此串行等待没有必要。我们把它们放进同一个并发窗口，同时为每一路设置独立超时。

```ts
const results = await Promise.allSettled([
  keywordSearch(query, { timeout: 45 }),
  vectorSearch(embedding, { timeout: 55 }),
  memorySearch(query, { timeout: 35 }),
]);

return mergeCandidates(results, { limit: 48 });
```

这里最重要的不是 `Promise.allSettled`，而是**允许局部失败**。知识检索不是支付交易；当一路召回超时，已有结果通常仍足以支持回答。

### 给候选数量设预算

候选越多并不必然带来更好的答案。重排成本近似与候选数成正比，可以写成：

$$
T_{rerank} \approx n \cdot (T_{encode} + T_{score})
$$

当召回结果从 120 条降到 48 条后，离线评测中的命中率几乎没有变化，重排耗时却下降了约一半。

## 重排：先去重，再让模型判断

过去每一路召回都会返回完整正文。相同文档的不同切片被反复编码，不仅浪费计算，也会挤占真正有差异的信息。新的合并策略先按文档与语义指纹去重，再交给重排器。

```text
召回结果 → 文档级去重 → 语义近邻合并 → 批量重排 → Top-k
```

批处理大小没有取理论最大值，而是根据线上数据选择了更稳定的区间。吞吐量与尾延迟之间需要平衡，最大批次通常不是最佳批次。

## 上下文：把 Token 当作预算

上下文拼装阶段引入了明确的 Token 预算。每段材料根据相关性、新鲜度和来源可信度获得分数，随后按预算装入提示词。

- 优先保留直接回答问题的证据；
- 同一来源只保留信息密度最高的片段；
- 为引用信息保留来源标识；
- 给模型指令预留固定空间。

这一步同时降低了延迟与幻觉率，因为模型看到的是更少但更集中的证据。

## 结果与边界

改造后，检索链路的 P95 从 310 ms 降到约 180 ms，首个 Token 的波动也明显减小。不过这不是一个可以永久保持的数字。数据规模、索引结构与外部依赖都会继续变化，因此我们把阶段耗时、候选数量和降级比例作为长期指标保留下来。

最终得到的经验很朴素：先观察，再缩短关键路径；先减少无效工作，再考虑更昂贵的基础设施。
